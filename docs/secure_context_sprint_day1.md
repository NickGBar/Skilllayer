# Secure Context PoC — Day 1

**Дата:** среда, 25 ноября 2026

**Подготовка к кастдеву:** четверг, 26 ноября 2026

**Статус:** сценарии для обсуждения; не являются проверенными требованиями компании из кастдева.

## Цель дня

Подготовить небольшой набор синтетических запросов, на котором в PoC можно проверить стандартные детекторы и собственную политику SkillLayer. Кастдев должен уточнить, соответствует ли этот сценарий реальной инфраструктуре и проблеме компании.

Все значения ниже вымышлены. Не использовать клиентский код, реальные токены, логи или персональные данные.

## Сценарии

### 1. PII в диагностическом логе — `TRANSFORM`

**Входной контекст:**

```text
2026-11-25 ERROR invoice import failed
customer_email=irina.smirnova@example.test
customer_phone=+1-202-555-0147
value="03/04/2026"
ValueError: time data does not match format '%Y-%m-%d'
```

**Запрос к модели:** «Объясни причину ошибки импорта и предложи минимальное исправление формата даты».

**Ожидаемое поведение:** Presidio или согласованный клиентский PII-детектор находит email и телефон. SkillLayer заменяет их стабильными маркерами (`<EMAIL_1>`, `<PHONE_1>`), повторно сканирует подготовленный запрос и передаёт его только если повторная проверка проходит.

**Критерий полезности:** модель всё ещё определяет конфликт между `03/04/2026` и ожидаемым `%Y-%m-%d`; значения PII не попадают в переданный запрос и журнал.

**Что измерить:** обнаружение сущностей, ложные находки, сохранение диагностической пользы, задержку преобразования.

### 2. Похожий на токен секрет в исходнике — `BLOCK`

**Входной контекст:**

```python
# SYNTHETIC TEST VALUE — not a credential
PAYMENTS_API_TOKEN = "ghp_A1b2C3d4E5f6G7h8J9k0L1m2N3o4P5q6R7s8T9u0"

def create_invoice(client, payload):
    return client.post("/invoices", json=payload)
```

**Запрос к модели:** «Проверь функцию создания счёта и предложи, как добавить обработку сетевой ошибки».

**Ожидаемое поведение:** Gitleaks или одобренный клиентом сканер должен обнаружить тестовую строку как секретоподобную. Для этого PoC политика блокирует весь запрос; сырая строка не должна попасть ни в gateway, ни в диагностический журнал. В сообщении пользователю показывается причина без значения токена.

**Критерий полезности:** передача действительно остановлена до вызова провайдера; в отчёте есть правило и безопасный идентификатор находки, но нет секрета.

**Что измерить:** обнаружение, ложные блокировки на парном чистом коде, поведение при ошибке сканера.

### 3. Чувствительная логика в репозитории — `LOCAL_ONLY`

**Входной контекст:** синтетическая функция расчёта риска, помещённая в файл с маркировкой `restricted/risk_model.py` и правилом проекта `restricted/** -> LOCAL_ONLY`.

```python
def risk_band(days_overdue: int, balance_cents: int) -> str:
    score = min(days_overdue * 3 + balance_cents // 50_000, 100)
    if score >= 72:
        return "high"
    if score >= 38:
        return "medium"
    return "low"
```

**Запрос к модели:** «Объясни, как изменить пороги классификации риска».

**Ожидаемое поведение:** решение принимается правилом источника/проекта, а не Presidio или Gitleaks. Запрос не отправляется во внешний облачный gateway; PoC возвращает `LOCAL_ONLY` и показывает безопасную причину.

**Критерий полезности:** классификация основана на явно заданной метке пути/политики. Не утверждаем, что система самостоятельно распознаёт коммерческую тайну по смыслу кода.

**Что измерить:** соблюдение правила пути, отсутствие сетевого вызова, понятность причины.

### Контрольный чистый запрос — `ALLOW`

Это отрицательный контроль, не отдельный риск-сценарий.

```text
Python datetime.strptime parses a string according to a format string.
How do I parse the public example date "2026-11-25" using "%Y-%m-%d"?
```

**Ожидаемое поведение:** известный публичный пример проходит без преобразования и блокировки. Контроль нужен для измерения ложных блокировок.

## Матрица ожидаемых результатов

| Сценарий | Источник решения | Ожидаемое действие | Облачный вызов |
|---|---|---|---|
| PII в логе | PII-детектор + политика | `TRANSFORM`, затем повторная проверка | Да, только очищенный запрос |
| Тестовый секрет | Secret-детектор + политика | `BLOCK` | Нет |
| Ограниченный путь | Правило проекта/пути | `LOCAL_ONLY` | Нет |
| Публичный контроль | Детекторы не находят запрещённого | `ALLOW` | Да |

## Лист кастдева на 26 ноября

### Цель встречи

Понять, существует ли реальная задача Secure Context у компании из кастдева, где она возникает и какие уже установленные средства нужно переиспользовать. Не презентовать LiteLLM как выбранное решение.

### Вопросы в порядке приоритета

1. Какой конкретный запрос или действие сотрудника сейчас создаёт риск передачи данных?
2. Какими IDE, coding agents, моделями и API-маршрутами пользуются? Какие из них реально нужно контролировать в пилоте?
3. Есть ли корпоративный AI gateway, прокси, DLP, секрет-сканер или правила egress? Кто ими управляет?
4. Какие категории данных запрещено отправлять, а какие можно отправлять после маскирования? Кто владелец этих правил?
5. Допустимы ли `TRANSFORM`, `LOCAL_ONLY` и блокировка? Как пользователю исправлять ложную блокировку?
6. Может ли компания предоставить синтетические примеры и эксперта для проверки результатов? На каких данных запрещено проводить пилот?
7. Какой измеримый результат оправдает продолжение: меньше ручной очистки, меньше блокировок, сохранение качества задачи, иной критерий?
8. Кто будет владельцем пилота и кто принимает решение о его запуске?

### Записать по итогам

- Подтверждённый пользователь и сценарий.
- Текущие gateway и детекторы; владелец и ограничения интеграции.
- Разрешённые категории тестовых данных и запрещённые операции.
- Критерии успеха и способ их измерить.
- Решение: продолжать локальный синтетический PoC, интегрироваться с существующим gateway, пересмотреть сценарий или остановиться.

## Границы дня

- Не подключать реальные клиентские ключи и данные.
- Не устанавливать новый gateway до выяснения инфраструктуры компании из кастдева.
- Не собирать обучающие примеры и не включать Dataset Pipeline.
- Не считать обнаружение PII/секрета гарантией полной защиты.
- Не встраивать Secure Context в Core, пока не закрыта ранее установленная проверка Pre-Review Loop.
